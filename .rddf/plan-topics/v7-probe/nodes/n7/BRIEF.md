# BRIEF — n7：失败模式与回滚可达性

## 目标

为「`build` 多 wave 并行实施通道」列出**失败模式**与**回滚路径**，并产出对既有 `plan` / `plan-worker` 机制反哺清单的第二部分。

## 边界（明确不做）

- 不重复 n3 的冲突分类（只消费「冲突会怎么失败」这一层）。
- 不重复 n4 的判据清单（只在其基础上写失败面）。
- 不执行真实回滚。

## 期望交付（`RESULT.md`）

1. **失败模式表**：至少 6 条，每条给出：失败模式 / 触发条件（具体操作序列）/ 可见症状 / **可检出性**（可机判 / 仅显示提示 / 不可检出）/ 现行兜底 / 残余风险。
   至少覆盖：并行写冲突、合并残留、中途中断、僵尸 worker、双活体写者、孤儿 worktree、上游语义漂移。
2. **回滚路径**：三步式（与本仓 ADR「回滚口径（X 步，回到现状）」体例一致），每步给出**动作 + 落点 + 可验证的判据**；并说明**哪些已落盘产物必须保留**、哪些必须清理。
3. **回滚条目草案**：按 `.rddf/rollback/plan-topics.json` 的结构给出一份草案条目（`edits[]` 的 `find`/`replace` 逐字节串位置、`notes`、`retire[]`），标明**哪些串必须逐字节钉死**以及原因。
4. ⭐ **对既有 `plan` / `plan-worker` 机制反哺清单（第二部分）**：逐条给出 `现象 | 依据 path:line | 建议动作`。
   候选至少覆盖：claim→spawn 两步无补偿（僵尸 attempt 需人工 reap）、reap 不吊销旧 worker（可复活 ⇒ 双活体写者）、topic 长锁无机械强制、并发下跨 node 污染的不可检出面、`owner` 字段被声明但不消费。
5. 至少 **8 处 `path:line` 引用**；正文 **≥ 100 行**；结论先行。

## 验收口径

- 失败模式表的「可检出性」列必须区分三种（可机判 / 仅显示提示 / 不可检出），不得全写「可检出」。
- 回滚路径每步必须有**可验证判据**（命令或断言），不得只写动作。
- 回滚条目草案必须指出**哪些 `find` 串必须逐字节钉死**，并给出钉死的原因（引用本仓既有的同型经验）。
- 反哺清单第二部分不得少于 4 条，且必须落到具体现象 + path:line。

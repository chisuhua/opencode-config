# BRIEF — n5：与 delegate 全局单槽的关系

## 目标

判定**「`build` 的多 wave 并行实施通道」与本仓既有的 `delegate` 全局单槽机制**之间的关系：是并存、替代、还是分槽。并给出冲突点清单与明确推荐。

这是本 topic 中**影响面最大**的一条 —— 它决定新通道会不会与既有「写隔离」纪律正面冲突。

## 边界（明确不做）

- 不改 `delegate` 的任何实现。
- 不重复 n2 的隔离方案选型（只消费其结论作为约束）。
- 不设计合并语义（n3）。

## 期望交付（`RESULT.md`）

1. **冲突点清单**：至少 4 条，每条给出：冲突描述 / 触发条件 / 涉及的不变式 / 依据 `path:line`。
   至少覆盖：槽位竞争、归属门控的 owner 语义、停机证据门控的适用性、`scope` 差集检测在多写者下的失效、以及新通道与 `PLAN_REF_ROOTS`「计划先行」门的关系。
2. **三种处置各自评估**：
   - **并存**（新通道自建槽位，与 delegate 槽并列）
   - **替代**（把 build 的实施纳入 delegate，`build` 只做编排）
   - **分槽**（按 `owner_agent` 细分槽位，扩展既有单槽语义）
   每种给出：改动面（哪些文件要动）、新增不变式、失败面、与既有 ADR 的冲突程度。
3. **明确推荐 + 明确否决项**：不得并列两个方案。否决项要写「否决理由 + 依据出处」。
4. **如果推荐「替代」**：给出 `build` 作为 delegate 调用方需要满足的前置条件清单（`plan_ref` 怎么办？`build` 产出计划吗？）。
5. **对既有 ADR 的影响面**：明确指出该决策会触及哪些既有 ADR 的哪一条决策（是「增补」还是「取代」）。
6. 至少 **8 处 `path:line` 引用**；正文 **≥ 100 行**；结论先行。

## 验收口径

- 三种处置的评估不得只写优点，必须各写至少一条代价与一条失败面。
- 推荐必须单一；若结论是「现在不该做」，也须给出**触发条件**（什么事实出现时应当重启该项）。
- 与既有 ADR 的关系一节必须点名具体决策编号（D1/D4/D7 等），不得只说「相关 ADR」。

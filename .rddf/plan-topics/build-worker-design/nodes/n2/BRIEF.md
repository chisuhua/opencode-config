# BRIEF — n2：写隔离方案选型

## 目标

为「`build` 多 wave 并行实施」这一目标，**选出写隔离机制**。产出可签批级论证：≥3 个候选方案的机制、隔离粒度、对现有不变式的影响、代价、失效模式，以及**明确推荐 + 明确否决项**。

## 边界（明确不做）

- 不写实现代码，不写具体命令序列。
- 不设计判据面（属 n4）、不设计合并语义（属 n3）。
- 不讨论「要不要做」这一层（属 n7 与最终合稿）—— 本节点只答「若做，用哪种隔离」。

## 期望交付（`RESULT.md`）

1. **候选方案 ≥ 3 个**，每个必须包含：
   - 机制（隔离如何建立、由谁建立、生命周期）
   - **隔离粒度**（进程 / 工作树 / 分支 / 目录 / 文件级）
   - **对现有不变式的影响**：逐条对照 —— 会不会破坏 `scope` 差集检测？会不会与 delegate 全局单槽冲突？会不会与 `PLAN_REF_ROOTS` 的「计划先行」门冲突？会不会让「单一写者」范式失效？
   - 代价（工程量、运维面、新增不变式、失败面）
   - 失效模式（该方案自身会怎么坏）
   候选至少覆盖：**worktree 隔离**、**分支隔离（同工作树）**、**目录/子树隔离**、以及**「不并行 + 上下文外置」**（把多 wave 需求换成别的解法）这一对照项。
2. **选项对比表**：每行含「结论 + 理由」，不得只写被选中的方案。
3. **推荐 + 明确否决项**：每个被否决方案写明「否决理由」（引用它与哪条不变式冲突）。
4. **隔离机制与写集粒度的关系**一段：说明在宿主能力下，写隔离最细能到哪一级（可引用 ADR 的上游语义事实），以及做不到的那一级的后果。
5. 至少 **8 处 `path:line` 引用**；正文 **≥ 100 行**；结论先行（第一屏给出推荐）。

## 验收口径

- 每个方案对「现有不变式的影响」一栏不得留空；写「无影响」也要给依据。
- 推荐必须是单一方案，不得并列两个「都可以」。
- 至少一个被否决方案的理由必须直接引用 D4 的单槽论证，不得自创理由。
- 「最细能到哪一级」一节必须区分**权限层强制**与**协议层约定**（本仓 ADR 对此有明确表述口径）。

# BRIEF — n3：合并与冲突语义

## 目标

给定 n2 的写隔离选型，**设计合并语义**：谁在什么时候把各路产物合到一起、合到哪里、冲突怎么判、每类冲突怎么处置、以及必须留什么痕。

## 边界（明确不做）

- 不选隔离方案（n2 已定，你只消费）。
- 不设计判据面的完整清单（n4 负责；你只提供「冲突判定」这一类的输入）。
- 不执行任何真实 git 操作。

## 期望交付（`RESULT.md`）

1. **合并模型**：谁合、何时合、合到哪（分支/主分支/临时集成分支）、合几次（每 wave 一次 vs 全部结束一次）、合的幂等性。
2. **冲突分类表**，至少 4 类，每类给：
   - 冲突形态（具体例子）
   - **判定方法**：可机判 / 需人判（明确标注）
   - 处置策略
   - 留痕要求
   至少覆盖：同一文件不同 hunk、同一文件同一 hunk、跨文件**依赖顺序**冲突（一方改了对方依赖的接口/类型）、**基线漂移**（合入时上游已变）。
3. **「不可机判」清单**：如实列出哪些冲突本质需要人裁决，并说明兜底（与本仓 ADR「已知不可机判清单」体例对齐）。
4. **与既有事务范式的关系**：合并是否需要「一次原子写内完成多件事」；若需要，锁的粒度与超时策略。
5. **合并产物必须入 git 的理由**（或反例）：与本仓「离线产物入 git」口径对齐。
6. 至少 **8 处 `path:line` 引用**；正文 **≥ 100 行**；结论先行。

## 验收口径

- 冲突分类每类都必须有「可机判/需人判」的明确标注，不许含糊。
- 「基线漂移」必须单独成类，不得并入「同一文件冲突」。
- 合并时机要给出**明确选择与理由**，不得写「视情况」。
- 若 n2 的 `RESULT.md` 尚未产出，本节点必须**两种分支都给结论**（隔离方案 A / B 各一套合并语义），并在文中标明当前实际依据的是哪一支。

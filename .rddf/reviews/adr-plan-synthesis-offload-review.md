## 1. oracle 第 1 轮（其他审查域）

**判定**：APPROVE —— 方向成立、机制已实测、否决项站得住；下列「必改」均可在 ADR 文本内闭合。

**7 个实质问题**：

1. **V5 的定义当前不可实现，且会把已验证的真实运行判红** —— oracle 建议的「deps ⊇（全部非 cancelled 节点 − 自身）」在追加式多合成节点下**两个合成节点都不满足** ⇒ 判据静默失效（真值轴根本不需要 `owner`：内容节点 = 全部非 cancelled 节点 − 合成节点自身）。
2. **「取消合成节点 + 重开」在 D9 语义下走不通** —— 父篇 `:130` 明确「禁止完成后取消」（`cancel` CLI 硬拒），而合成质量不达标的典型场景恰是 `m1` 已 `done` ⇒ 该路径是死路 ⇒ 可行解是**追加式**（新增 `m2`，`m1` 留作审计痕迹）。
3. **V4 按现草图不可机械实现** —— 缺两个约定：① 上游「最重/必须上报」须携带**稳定 token**；② 「结论层」必须机器可定位（BRIEF 的五节固定结构正是使能条件）。
4. **V4/V5 的载体未命名，与 D5 的闭集承诺正面相撞** —— 「零新增判据」「不加违规码」「`plan-topic-check.ts` 零改动」「B1 判据 CLI 加 V4」四个承诺不可能同时成立 ⇒ 必须二选一命名载体。
5. **B0 的投影落点未点名** —— 父篇 #19 与主题文档 §10 仍写「SYNTHESIS.md 是否入表待定」，与 D2「本篇闭合 #19」矛盾。
6. **「B0→B1 之间语义无锚点保护」是伪窗口；真风险在 provider 层** —— 锚点只能钉上游源码，**钉不住 provider 是否真换模型** ⇒ 落到父篇残留 #18 的悬挂 attempt 缺口；该风险只在散文中，未进不可机判清单。
7. **「合成结果的作者 vs 背书者」未被回避但未被写出** —— 一句话即可闭合。

**oracle 对本篇推理的对抗裁定**：Q1a「成立，且比你说的更糟」；Q1b「你的『该写成不可机判而不是 V5』不成立 —— ADR 已经两头都写了，病在 V5 的**定义**」；Q1c「成立」；Q2「第一击成立，但『取消 ⇒ topic 失去答案』在追加式 m2 下消解；第二击半成立」；Q3b「你**高估**了 V4 对观测到的失效模式的覆盖缺口 —— X2 是被标了的，V4 判的正是这种」；Q3c「除字面张力外还有三个上游风险」。

### 5.1 ⚠ 本次验收中观察到的一次**瞬时假红**（已定位，非本篇改动引起）

**现象**：Status 转 `Proposed` 后第一次跑 `bun test tests/` ⇒ **1231 pass / 1 fail**；随后**连续 3 次全绿**（1232 pass / 1 skip / 0 fail），无法复现。

**定位**：**`tests/config-guards.test.ts` 的 `AC10④`（父篇 ADR 的 commit 必须是代码 commit 的祖先）** —— 该用例对**真实仓库**跑 3 次 git 子进程（`git log -1` 走 pathspec 全历史 + `git log -1 -S<锚点>` + `git merge-base --is-ancestor`）。该用例自带注释已登记此类风险：「常态 0.2–0.3s，但**负载尾部实测 5.0–5.1s，会越过 bun 默认的 5000ms 每用例超时 ⇒ 假红**（且文案读起来像「父篇滞后」的真问题 ⇒ **把排查引向 ADR 提交顺序，而不是机器负载**）」。

**本机实测**：那 3 个 git 子进程在**空闲**下耗时 **592–1483 ms**（5 轮），**明显慢于仓里校准 20s 超时所用的基线（0.2–0.3s）** ⇒ 该用例的 20s 超时在本机**余量远小于仓里记录的机器** ⇒ 负载下更易假红。

**结论与建议**：
1. **与本篇改动无关**（该用例判的是**父篇** `ADR-plan-delegate-engineering-session` 与 `lib/delegate-core.ts` 的提交先后，本篇不在其射程）⇒ **不构成对本篇的 BLOCKER**。
2. ⚠ **但它是一个应登记的仓级风险**：**本仓唯一真实闸门含一个对 git 负载敏感、且失败文案会把排查引向错误方向的假红面**。建议（另立条目，**不属本篇**）：
   - 该用例的超时应按**本机**的负载尾部重估（当前 20s 相对本机 1.5s 空闲基线 ⇒ 余量约 13×，但 pickaxe 全历史扫描的尾部未知）；
   - 或把 `git log -S<锚点>` 换成**预先算出的锚点 commit 常量**（该锚点是稳定的决策行 ⇒ 可固化 ⇒ 免掉全历史扫描）；
   - 或至少在用例失败文案里加上「**可能是 git 负载导致的假红，先重跑一次**」的提示。
3. **操作纪律**（本轮采纳）：**批量编辑文件后第一次跑闸门不轻信** —— 若为瞬时红，**重跑一次再判定**；本次即因此避免了把假红误判为本篇引入的回归。

## 3. 上下文成本实测（**修正方案稿 §5 的口径**）

### 3.1 计量口径的修正（重要）

- `session_v2.tokens_cache_read` **不可用作单次测量口径** —— 实测读一个 27 KB 文件期间它涨了 **32,157,824**（累计 provider 侧计数，含每轮整上下文重发）⇒ **本记录一律不引用它**。
- `tokens_input` = **当前上下文大小**（非累计）：根会话从 660,577（派发前）单调增长到 891,942 ⇒ 与「上下文里多了什么」一致。
- ⚠ **此前「读 7 份 RESULT = +64,941 tokens ⇒ 0.265 tokens/byte」这个口径混淆了内容与轮次开销**（4 次 read 工具调用 + 随后的分析轮都把已读内容重新计入）⇒ **该数字只能作为「根会话上下文增量」读，不能当「净内容成本」**。方案稿 §5 的「每节点 ≈ 9,277 tokens」同理偏大。**方案稿须据此改写。**

### 3.2 可辩护的实测结论

| 量 | 实测 | 口径 |
|---|---|---|
| **merger 隔离会话的最终上下文** | **132,909 tokens** | 它完成了「读 244,703 B × 7 + BRIEF + TOPIC + 产出 27,112 B 合成稿 + 31 项裁决」的**全部**工作 |
| 根「自己做」路径的上下文增量 | **+114,842** | 相对派发前基线（实测） |
| 根「外置」路径读合成稿的增量 | **+2,134** | 紧邻 read 前后的快照差（实测） |
| 根的**材料吸收量** | 244,703 B → **27,112 B**（**-89%**） | 根不再吸收 7 份子产出，只吸收 1 份合成稿 |

⇒ **外置的收益因此比方案稿原先的推算更硬**：
- 方案稿原估：根 per-topic 114,842 → 56,174（**-51%**，解析推导）
- 实测口径：根的**材料吸收**降 89%（244,703 B → 27,112 B）；**合并工作整体移入一个 132,909 tokens 的隔离会话**，根不再背着它
- ⇒ **准确表述**：外置把「244 KB 的子产出」从根上下文里移走，代价是「多一个 133k 的隔离会话」

⚠ **仍未实测**：**S2/S3 需要一个「从未读过 7 份 RESULT」的新根会话**才能给出干净的 per-topic 数字（本会话已吸收过全部材料，增量不可归因）⇒ **探针规格见 §5.3**。

## 4. §3 阶梯的裁决：C 档 ⇒ **升 A 档**

| 档 | 结果 | 依据 |
|---|---|---|
| **C**（弱模型合并，无 model 覆盖） | ⚠️ **部分达标**：① PASS、③ PASS（优于判据）、② **丢 1 条被标为「最重」的定义** | §2.3 |
| **A**（派发覆盖模型） | ➡️ **下一档** | 零 paperwork（不新增 agent / prompt / 配置 / 守卫 / 回滚清单）；**但**与 `subagent` 工具说明「NEVER set this unless the user explicitly asks」相抵 ⇒ 需 architect 一次显式裁决（方案稿 M7 / S8） |
| **B**（新增 `plan-merger` agent） | ⏸ 若 A 档仍丢 ⇒ 兜底 | 一条 ADR + 双审 + 新 prompt + 守卫 + 文档投影 + 回滚字节钉死 |

⇒ **阶梯被实测验证**：C 档不是「直接可用」，但它**便宜到足以先验**，且它把「弱模型会丢什么」**具体定位到了「显式标为最重的发现会被降级」**这一种失效模式 ⇒ **A 档只需针对这一种**（更强的模型 + 更强的「最重项必须进结论层」的指令）⇒ 期望 A 档能补上 X2。

⇒ **不选 B 档的理由**：A 档与 B 档的差别只在一处失败上，而 A 档的增量成本是**零 paperwork** ⇒ **先 A，B 只在 A 也失败时启用。**

# 测试体系覆盖面审计 — 一次性报告（不入库为常设矩阵）

> 日期：2026-11-15 ｜ 触发：用户「思考更全面的测试集来覆盖更多情况」
> 性质：**一次性审计报告**。按 metis 的建议，**不**新建常设「测试体系」文档 / 常设覆盖矩阵
> （那会变成第三份 doctrine 副本 —— `docs/test-authoring.md` 与 `docs/guard-authoring.md`
> 本身已是两份**无守卫**的 doctrine 副本）。
> 方法：oracle（成本/收益视角）+ metis（失效模式视角）双向挑战 ⇒ 结论已在本批落地

## 1. 实测的起点：覆盖面是**长出来的**，不是设计出来的

| 指标 | 实测 |
|---|---|
| 用例总数 | **577 → 581**（本批 +4） |
| `config-guards` 的扫描面分布 | `prompts/**` 引用 22 次、`lib/**` 3 次、`docs/**` 2 次 |
| 零守卫的投影面（我的初判） | `prompts/{explore,librarian,metis,general}.md`、`lib/{subagent-contract-core,model-fallback-core}.ts`、`lib/delegate-async.ts` |

⇒ **每一次事故加一条守卫** ⇒ 覆盖面 = 事故史，不是对象清单。

⚠ **但我的统计本身有错**（metis 指出并核实）：
- `prompts/metis.md` **不是零守卫** —— `config-guards.test.ts` 以它为**真源**做三处有序全等；
- `lib/model-fallback-core.ts` 有 33 条单测且是**真源**（无投影副本）⇒ 它**不属于**「投影面」这一轴
  （**「有测试」≠「有守卫」是两个正交轴** —— oracle 的初版矩阵把它们混了）。

⇒ **教训**：连「哪些面该有守卫」都要先分清**轴**（行为测试 / 投影漂移守卫 / 守卫是否被规范命令执行），
否则矩阵会既误报又漏报。

## 2. 核心结论（两个 subagent 独立收敛到同一处）

### 「全面」**不可达** —— 但有可达的替代

判据体系**原则上无法自证完备**（本次就是实例：oracle + metis + critic **三方共享同一心智模型**
⇒ **同时**漏掉「消费端三点 diff 在未提交工作树恒空 ⇒ 基线对照无判别力」，直到 metis 第 2 轮才提出）。

⇒ 正确目标不是「全面」（一个**状态**），而是**对增量的门**（一个**机制**）：

| 件 | 形态 | 本批状态 |
|---|---|---|
| **① 增量门** | 每个新投影面出现时**机械地**逼一次决定：建守卫 / 登记 / 排除 | ✅ **部分落地**：新增**文件**闸门（可机械）；「已有文件里新增陈述」**不可机械**（属 review 流程） |
| **② 盲区如实登记** | 单点、机读的登记表 | ⚠ 登记表**当前为空**且**有已知局限**（只能承载「有对应红判据」的盲区 ⇒ 承载不了「非 `.md` 后缀的陈旧副本」）—— 已写进代码注释 |
| **③ 每类盲区有已验证会红的判据** | 登记 ≠ 免死牌 | ❌ **当前不可机判**：本仓守卫都是内联 `expect()`，**不是** `check(text) => violations[]` 纯函数 ⇒ 只能「人工声称演练过」⇒ 已登记为 backlog（见 §5） |

### 分层**塌缩**（oracle）：L1/L5/L6/L7 **不是层，是横切技术**

- **L1（结构层）**：其存在理由可通过**渲染器派生**消灭 ⇒ 派生后守卫回归普通逐字比对
  ⇒ 本批已做（dispatch 的必填/选填清单改为从 schema 现算）。
- **L5（变异层）**：与「逐分支注入演练」重复；且经典变异框架的 mutant 分布与本仓威胁模型
  （**契约漂移/手抄**，非算术错误）错位 ⇒ 不建框架，**只把已有的 revert 演练系统化**。
- **L6（差分层）**：本仓已有半套实践（成对 describe + 有意差异已被断言为事实）⇒
  正确形态是「**共享语料表 + 差异登记表**」，语料**搬迁**而非新建。
- **L7（性质层）**：值得做的性质用普通参数表即可 ⇒ 不引 PBT 库。

⇒ 8 层 ⇒ `docs/test-authoring.md` §1 的 **4 层** + 三个横切附件。

## 4. 本批**没**做（及原因）

| 项 | 原因 |
|---|---|
| 常设「测试体系」文档 / 常设覆盖矩阵 | 会变成第三份 doctrine 副本；**本报告一次性即可** |
| 行指纹（oracle 提议） | 锚的是**位置**不是**决定**；且「只改注释就红」会制造「没人愿意动那一行」的负担 ⇒ 改用 `redTest` + `expiresOn` 字段（但需先有可验证会红的判据，见 §5） |
| 注入配方表（每守卫族一条 snippet） | 会变成「写下来但没人重跑的脚本」（`verify_arch_docs_scope.sh` 已是该命运的实例）⇒ 配方应写在 test **内**（不跑就会红） |
| Stryker / fast-check / LLM-as-judge | mutant 分布与威胁模型错位 / 收益≈0 / 违反「判路径不判措辞」的 doctrine |
| 手维护「事实 × 投影面」主矩阵 | 「投影面」的定义是**语义**的 ⇒ 手维护必然腐化 |

## 5. backlog（**唯一能让「已验证可捕」可机判的路径**）

> **把判据提炼成纯函数**（`verifierWriteSetViolations(text, canonical): string[]`），
> 再由元测试遍历登记条目的 `redTest`、喂入注入文本、断言 `violations.length > 0`。
>
> ⚠ **工作量被低估了**：本仓守卫都是内联 `expect()` 作用在 `readFileSync` 结果上 ⇒
> 要变成纯函数形态，需动 **12 个 describe 家族** ⇒ 工作量是 oracle 原排期的 **3–5 倍**。
> ⇒ 本批**只对新增的守卫**用纯函数形态写，作为范式样本（本次新增的 3 条仍是内联形态 ——
> **如实登记为未做**，不假装）。
>
> 前置依赖：守卫函数与「读文件」解耦 ⇒ 需要一个「判据函数接受文本、返回违规列表」的约定。

## 6. 一句话给后人

> **本仓的覆盖面是事故史，不是设计。** 想让它不再是事故史，靠的不是「多写测试」，
> 而是**每个新增投影面都机械地逼一次决定**（建守卫 / 登记 / 排除）——
> 而「登记」只有在**有可验证会红的判据**时才有意义。

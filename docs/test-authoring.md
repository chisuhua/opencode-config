# 测试构建指南 —— 从「要验什么」到「怎么建一条不会骗你的测试」

> **状态**：2026-11-15 起（`v2.25`–`v2.28` 三批 + e2e `CS-1`–`CS-7` 的实践沉淀）
> **面向**：要**新增一条测试**的人 —— 先决定写在哪一层，再写。**不含**某条测试的具体内容。
> **冲突裁决**：本文与 `prompts/build.md` / 测试实现 / `lib/**` **冲突时一律以后者为准**。
> 本文是**方法论参考**（非契约）；带表格的段落是某一时点的快照。

## 0. 与另三份文档的分工（别在错的地方找答案）

| 想知道 | 看 |
|---|---|
| 本仓这套代码的测试**在哪、怎么跑**、fixture 约定、覆盖矩阵 | [`front-delegate-testing.md`](./front-delegate-testing.md) |
| **判据/守卫本身怎么写**（真源→渲染→投影→逐字比对）、变红演练、已知陷阱 | [`guard-authoring.md`](./guard-authoring.md) |
| 需要**真实运行时**的用例怎么断言（三条纪律 + 变红演练） | `rdd-workflow-e2e` 仓的 `docs/runtime-assertion-discipline.md` |
| **该写哪一层、怎么保证这条测试不骗人**（TDD 有效红灯 / 确定性 / 断言对象 / 门控） | 本文 |

> 「运行时验证」≈「行为端到端」，「验收判定」≈「手工验收」。

## 1. 先选层：四层各自能证明什么（也各不能证明什么）

选层错了，写再多断言都是自我安慰。判定顺序：**能静态判的不要用运行时判**（贵、慢、吃额度、受环境影响）。

| 层 | 跑在哪 | 能证明 | **不能证明** |
|---|---|---|---|
| **静态契约** | `bun test tests/`（本仓；离线，进 CI 属**规范性**要求，见 §5） | 真源 ↔ 投影一致（常量 ↔ 机读块 ↔ prompt 措辞）；配置 ↔ 文档一致 | **运行时真的按契约走**。prompt 写了 ≠ agent 照做；契约有字段 ≠ 宿主真的填了 |
| **纯逻辑单测** | `bun test tests/`（假 ctx；同上，进 CI 属规范性要求） | 纯函数/工具的行为、分支、边界、错误路径 | 宿主接线（插件能否加载、权限层实际裁决、真实 session 被不被驱动） |
| **行为端到端** | `rdd-workflow-e2e`（`E2E_REAL_RUNTIME=1`，默认 skip） | **真实发生的事实**：真派一个 session、插件真的返回某形状、派发方真的按纪律转述 | 契约漂移（它只测被驱动到的那条路径）、成本可控性（每条都吃真实额度） |
| **手工验收** | 人工按 AC 逐条跑 | 跨系统、需要人判断的面 | 可重复、可回归、CI 拦截 |

> **手工验收不是兜底选项**：跨系统集成、需要人判断的面、ADR Verification 里不可机械化的条目，
> **只有这一层能覆盖**（`prompts/build.md` 的 verifier 契约里，未命中 skill 时走的是**含人工判断成分的本地验收**）。
> 上表的「不能证明」列是**分工**，不是**贬低**。

**真实判例（为什么必须有行为层）**：`v2.28` 建的静态守卫能证明「派发方 prompt 覆盖了关键字段 + 写了纪律句」，
但证明不了「agent 拿到 `unverified` 之后真的不把它当完成」。⇒ 另建 `CS-7`（真派一个只读回答的后端，
断言 `outcome=unverified` / `host_outcome=succeeded` / `no_work_evidence=true`，且派发方文本含规定短语、
不含「已完成」）。**两层不能互替，缺哪层就缺哪层的证明力**。

> ⚠ **推论（最容易犯的错）**：不要把「我在 A 层建了测试」说成「A+B 都被覆盖了」。
> 宣称的覆盖面**不得超过**所建层能证明的范围；覆盖不到的面要么补层，要么登记为已知边界。

## 2. TDD：什么才算「有效红灯」

**红灯不是「有测试失败」，而是「失败在预期的那条断言上，且该失败模式是真实的」。**

三种**无效**红灯（都会让你误以为走在 TDD 上）：

| 形态 | 为什么无效 | 处置 |
|---|---|---|
| **加载/编译失败** | 整文件没跑起来 ⇒ 一条断言都没执行 ⇒ 绿灯时也不知道测到了什么 | 把「符号不存在」表达成**一条断言失败**：动态 `import()` + 在 `test()` 内断言导出存在 |
| **断言写错方向** | 红灯来自自己写反的期望值，不是被测行为 | 红灯时读失败信息，确认它说的是**你预期的那个缺陷**（守卫侧的同一条规则：`guard-authoring.md` §3.2）|
| **分支不可达** | 判据那一支根本没被执行（正则不产出 token 之类）⇒ 绿灯是假的 | 逐支做注入演练，见 `guard-authoring.md` §3.1/§3.2 |

**「当场即绿的测试」是合法类别，但要如实标注**：防漂移守卫是**照现有实现**写的（例：`v2.28` 的 AC22
「契约字段集 ↔ 插件 `summary` 键双向一致」），它没有红→绿过程，价值在于**将来**漂移时变红。
⇒ 记录里写「当场即绿，属防漂移守卫」，**不要**事后编一个假红灯叙事。

> ⚠ **「如实标注」只是登记，不是免除**：防漂移类**必须**附带一次注入演练记录
> （做法见 `guard-authoring.md` §3.1 —— 不在此复述步骤）。
> 没演练记录的「防漂移」标注不被认可 —— 否则「我这条是防漂移守卫」会变成免掉红→绿的后门。

## 3. 断言：只认事实；措辞只在「被规定」时才是判据

### 3.1 断言对象优先结构化字段

```python
# ✔ 断言事实
assert d["kind"] == "engineering"
assert d["outcome"] == "unverified"
assert d["write_tool_calls"] == 0
```

```python
# ✘ 断言自由措辞（模型换个说法就红/绿，与被测行为无关）
grep -q "后端已完成" output
```

**优先级**：先断言「**发生了什么**」（结构化字段），再断言「**为什么**」（原因/顺序等描述）。

### 3.2 「规定措辞」是唯一例外

当**契约明文规定**某个短语时（例：prompt 要求「必须转述为『没有可验证的交付证据』」），
断言那个短语是**契约检查**，不是自由措辞检查 —— 它验的是「agent 照 prompt 做了」。
⇒ 判据：**该短语是否在契约文本里逐字存在**。是 ⇒ 可断言；否 ⇒ 不许断言措辞。

### 3.3 要在「调用方真正看到的形状」上断言

内存对象与**序列化后**的对象可以不同。真实案例：`wait_error: waitError` 在成功路径恒为
`undefined` ⇒ `JSON.stringify` **丢键** ⇒ 线上 payload 少一个字段，而「用 `in` 判内存对象」的自检
与「扫源码」的静态守卫**都看不见**。⇒ 对该类契约，断言/自检跑在
`JSON.parse(JSON.stringify(x))` 上。

> ⚠ **作用域边界（别泛化）**：只在对象**会跨序列化边界离开当前进程**时才这么做
> （插件返回值 / 写入 state 文件 / 网络传输）。纯内部对象**不要**加序列化往返 ——
> `undefined` 静默丢键会让测试看到的世界与实现看到的世界不一致，反而掩盖真实的值错误。

## 4. 确定性：伪造的外部状态必须**必然**成立，不能「可能」成立

**flaky = 判据依赖了「恰好」**。修法不是加重试，是把「可能」改成「必然」。

### 4.1 真实判例（`tests/delegate-async.test.ts` 三条 tripwire 用例）

伪造成「另一个存活实例」用的是 `{ pid: process.pid + 1, host: <本机> }`，
而 survived 判定是「**同 host 才查 pid 存活**」⇒ 成败取决于 `pid+1` **恰好**是否存在
⇒ 实测 3 次运行中 1 次 3 条全红。

**两个错误叠在一起**：① 用「可能存活」的 pid；② 伪造方式与该文件里另一条用例
（明写「同 host 的死 pid 不算实例；**跨 host 保守视为存活**」）的语义**相反**。

### 4.2 三条可复用的修法

| 修法 | 做法 |
|---|---|
| **用环境真值派生「必然」值** | 「必然死亡」的 pid = `/proc/sys/kernel/pid_max + 1`，而不是硬编码 `999999`（**有概率撞上真实进程** ⇒ 同类 flaky） |
| **选一个语义上必然成立的方向** | 伪造 foreign 实例一律**跨 host** ⇒ 实现**不查 pid**、保守视为存活 ⇒ 与 pid 无关 |
| **加回归断言钉住「为什么它是确定的」** | 断言「跨 host + 必然死亡的 pid ⇒ 仍算存活」。实现若改成「跨 host 也查 pid」⇒ 该用例变红 ⇒ 提醒改回 |

### 4.3 验证方式

**先证明失败模式真实**（把「必然」值注入 ⇒ 目标用例**全部** FAIL），**再修**，修完
**连跑 5 次以上**（`for i in 1..5; do bun test <file>; done`，看退出码）。

> 只跑一次绿 ≠ 不 flaky。原始症状本身就是「3 次里 1 次红」。
>
> ⚠ **两个判据强度不同，别只做弱的**：上面第一条（注入必然值 ⇒ **100% 红**）是**逻辑判据**；
> 「连跑 5 次」只是**经验下限**（复现率 1/10 时，5 次全绿的概率 0.9⁵ ≈ 59% ⇒ **漏检约 59%**）。怀疑复现率低 ⇒
> 回到第一条去证明**必然性**，不要靠加跑次数碰运气。

## 5. 门控：需要真实运行时/模型的测试默认不进 CI

| 层 | 门控 | 理由 |
|---|---|---|
| 静态 + 纯逻辑单测 | 无门控，**必须**进 CI | 离线、快、确定性 |
| 行为端到端 | 环境变量门控（如 `E2E_REAL_RUNTIME=1`），**默认 skip** | 吃真实额度、需要真实宿主、偶发环境故障会把 CI 变成噪音 |

> **「进 CI」是规范性要求，不是现状描述**：本仓 CI **尚未接入**（见
> `front-delegate-testing.md` §10 的接入建议）。它的意思是「符合进 CI 的条件，接入后即纳入」——
> 不要据此以为「已经有人在 CI 上跑」。同理，本表**不是**「本仓已有这些层」的宣称。

**不要「顺手」把行为层塞进 CI**：一条需要真实模型的用例在 CI 上失败时，你无法区分
「实现坏了」和「环境/额度问题」⇒ 判据失效（正是「取证不可用不得判 pass」要处理的那类）。
需要时**手动/定时跑**并记录实跑证据（真实输出片段，不是「应该能过」）。

## 6. 演练与判红（细节在 `guard-authoring.md`，此处只列测试侧差异）

**测试侧唯一的差异**：演练形态是**先红后绿**（先看到预期失败，再写实现），而守卫侧是
**注入陈旧陈述**（往活文档/配置注入 ⇒ 守卫必须红）。

其余三条**同守卫侧，不在这里另立一套**：

- 有效判据 = 失败信息指向**预期的那条断言** → `guard-authoring.md` §3.2
- 判红信号 = **只认退出码**（非 TTY 下失败明细在 stderr，数 stdout 的 `(fail)` 行会永远假绿） → 同 §4.4
- 改配置 = **外科式文本编辑**，不要 JSON 往返（会把配置整份重排） → 同 §4.4

> ⚠ 上面三行是**指针**，判据真源在 `guard-authoring.md`。它若改口径，改那边即可 ——
> 本文不复述细节（复述即漂）。

## 7. 新增一条测试的决策流程

1. **要验的是什么？** 写一句话，必须是**可观测的事实**（不是「应该没问题」）。
2. **哪一层能观测到它？**（§1 表）能静态判就静态判；只有「运行时才存在的事实」才上行为层。
3. **该层的红灯长什么样？** 先写出会失败的断言（§2）。若它当场即绿 ⇒ 确认它是**防漂移**类，
   标注**并补一次注入演练**（注入陈旧值 ⇒ 变红 ⇒ 还原 ⇒ 绿）。
4. **断言对象是事实吗？** 结构化字段优先；要断言措辞 ⇒ 先确认契约里逐字规定了它（§3）。
5. **伪造成立吗？** 注入的每个外部状态都是**必然**成立的吗？不确定 ⇒ 改成环境真值派生 + 回归断言（§4）。
6. **它该进 CI 吗？** 需要真实模型/宿主 ⇒ 门控 + 默认 skip（§5）。
7. **覆盖宣称核对**：我现在能说「哪一层证明了什么」？**不得**超出所建层（§1 推论）。
8. **收尾**：跑全量 + 单独校验退出码；更新受影响文档里的**计数与字段数**（回读实测值，不凭记忆）。

## 8. 核对单（写完一条测试，逐条过）

- [ ] 选层与「要验的事实」匹配？没有用静态层去"证明"运行时行为？
- [ ] 红灯**指向预期的断言**，且不是加载失败 / 断言写反 / 分支不可达？（当场即绿 ⇒ 已标注为防漂移类**且有注入演练记录**）
- [ ] 断言对象是**结构化事实**？措辞断言只用在**契约逐字规定**的短语上？
- [ ] 跨序列化边界的契约断言跑在**序列化之后**的对象上（值 `undefined` 会丢键）？纯内部对象**没有**多此一举？
- [ ] 伪造的外部状态**必然**成立（环境真值派生），而非「恰好」？有一条回归断言钉住该依据？
- [ ] flaky 先证明了**必然红**（注入必然值 ⇒ 100% FAIL），再谈「连跑 ≥5 次」？
- [ ] 需要真实运行时的用例已门控、默认不进 CI？实跑证据是**真实输出**而非推断？
- [ ] 覆盖宣称 ≤ 所建层的证明力？覆盖不到的面已在注释/文档里**登记为已知边界**？
- [ ] 判红用的是**退出码**，不是数文本行？演练改配置用**外科式编辑**？

## 9. 触真实仓历史的守卫：预算与唯一入口

**适用**：判据要在**本仓真实历史**上跑 git（不是 `mkdtempSync` 出来的 fixture 仓）。典型 = 祖先判定/基线取法类的守卫。

**为什么单列一章**：真实仓查询的成本**随提交数增长**，且 pathspec 查询（`git log -- <path>`）会走全部提交的树。
bun 默认**每用例 5000ms** 超时 ⇒ 负载尾部一旦越过就是**假红**，而 `verify_commands` 含 `bun test tests/`
⇒ 假红 = **随机拒提交**，且失败文案读起来像判据本身失败（误诊方向）。

**规则（三条，缺一条就是缺口）**：

1. **唯一入口**：真实仓 git 只能经 `tests/helpers/real-repo-git.ts` 的 `lastCommitShaInRepo` / `isAncestorInRepo`。
   **不要**在测试文件里直接 `execFileSync("git", …, { cwd: <仓根> })` —— 元守卫 `tests/real-repo-git-budget.test.ts`
   会因「`cwd` 指向仓根」而**红**。三种等价写法都算：字面含 `import.meta.dir` / 同文件里由它**派生**的常量
   （含传递闭包：`const B = path.join(A, "..")`）/ **`process.cwd()`**；**省略 `cwd`**（隐式继承进程 cwd = 仓根）同样**红**。

   > ⚠ **本闸门只约束成本形态，不授权弱化判据**：把真实仓判据改写成 fixture、删清单项、调低预算常量、
   > 或把 `cwd` 写成形参以绕过检测 —— 这些都是**改判据强度**，不是「让闸门变绿」的手段，须另走变更。
2. **两层预算，禁止一个常量承担两种语义**：用例级 `REAL_REPO_GIT_TEST_TIMEOUT_MS = 20s`（守卫写成 `{ timeout: 该常量 }`）
   + 每次调用 `REAL_REPO_GIT_CALL_TIMEOUT_MS = 6s`（算式 `3 × 6s = 18s < 20s`）。**禁重试**（重试会把「一次慢」放大成「必然超用例」）。
3. **超时不得被吞**：per-call 超时（`err.code === "ETIMEDOUT"`）必须**抛带指引的错**；`lastCommitSha` 的
   「出错 ⇒ 空串 ⇒ 跳过」只针对**非超时**失败（无 git / 非零退出 / 浅克隆）。吞掉超时 = 判据**静默消失**，比假红更坏。

**新增第二个消费者时**：在 `tests/real-repo-git-budget.test.ts` 的 `REAL_REPO_GUARDS` 清单里加一行
`{ file, testTitle, budget }`（`budget` = 该 `test(...)` 块内 helper 调用点数 ⇒ 静态计数，多/少都红）。
**不要把超时值抄进清单** —— 唯一真源是源码里的 `{ timeout }`，守卫读取并校验它 ≥ 用例级常量。

**已知漏检面（静态检测的固有代价，登记而非假装覆盖）**：形参式 git helper、`cwd` 是局部 fixture 变量
（`dir`/`repo`/`dest`/`project`）、其它指向仓根的等价写法（`new URL("..", import.meta.url).pathname`、
带类型标注的 const、多行种子声明、`path.resolve()`、从 env 读到的绝对路径 —— 今日仓内零作为 `cwd` 使用）、
`tests/probes/**`（非 `*.test.ts`）、`Bun.spawnSync([…"git"…])`（**实测**，突变 M6 不红）、
`git -C` / `bash -c "git …"` / `process.chdir()` / `GIT_DIR` 泄漏。要精确区分真实仓与 fixture 只能靠
PATH shim / `bunfig.toml` preload 记录全量轨迹 ⇒ 那要改进程启动配置，本仓不做。

> **fixture 仓不受这条规则约束**：`mkdtempSync` 里 1–2 个提交的仓成本可忽略；把规则套上去只会稀释成噪音。

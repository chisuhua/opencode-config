# Design — independent-build-session-e2e

> 判据真源：`proposal.md` 的「## 验收标准」（AC1–AC8）。
> 前置：层 1（本仓静态守卫，describe「独立会话机制」，7 条）已落地 —— 它证明「**文档写了**」，
> 本 change 证明「**agent 照做了**」。

## D1. 断「状态事实」，不断「模型措辞」

e2e 的最大风险是 **flaky**：模型措辞每次都可能不同（"好的，我来切换" vs "已切换到 verifier"）。
⇒ 三条用例的断言分两类：

| 用例 | 断什么 | 为什么稳 |
|---|---|---|
| E-1 | 首行的**形态**（`【角色: builder` 开头 + `】` 收尾） | 形态由 prompt 规定；措辞部分不判 |
| E-2 | ① 首行含 `【角色: verifier`；② **`role.json` 的 `current_role === "verifier"`** | ② 是**磁盘状态事实** ⇒ 模型措辞再变也红不了 |
| E-3 | 三要素的**关键词族**（拒绝 / 解释 / 引导） | 判「族」而非单句 ⇒ 措辞可变仍能过 |

⇒ **E-2 的第 ② 条才是真正抗 flaky 的那条** —— 它是本 change 的核心断言。

## D2. 怎么跑「独立会话」

e2e 仓既有做法（`test_subagent_contract_runtime.bats`）：

```bash
opencode run --standalone --agent build --session "$sid" --format json "$prompt"
```

- `--standalone`：不起服务、独立进程（⇒ 不受本机服务状态影响）
- `--session "$sid"`：**复用同一 session id** ⇒ E-2 的「第二轮」能接着第一轮 ⇒ 才能验证「切换」是**状态变更**而非两个独立会话
- `--format json` ⇒ 逐事件 JSON，便于取「首行文本」

⚠ **必须用独立 HOME**（e2e 仓既有做法：`HOME="$SC_HOME" OPENCODE_DB="$SC_DB"`）⇒ 不污染真实环境的状态文件。

## D3. 门控与额度

- 默认 **skip**（`E2E_REAL_RUNTIME` 之类开关未开 ⇒ 0 条真跑）⇒ 不吃 CI 额度；
- **额度不足 ⇒ skip**（`provider.rate-limit`）—— 与 e2e 仓既有约定一致（**取证不可用不得判 fail**）。

## D4. 为什么只覆盖 builder + 一次切换

- 逐角色的开场报告措辞差异属**静态层**（层 1 已钉「每个角色的格式是 `【角色: X …】` 形态」）；
- 行为层要证明的是「**机制会动**」⇒ 一个角色 + 一次切换足以证明；
  ⇒ 六角色逐个跑 = 额度换不来新信息。

## D5. 授权窗口的自动切换为何不做

需要**真实多轮交互**（窗口内自动切换要连续多回合才触发 `used` 递增）⇒ 额度与时长成本高，
且**易 flaky**（模型可能不按窗口规则切换 ⇒ 分不清是「机制坏」还是「模型没照做」）。
⇒ 本 change 只钉「机制存在」（静态层的字段集判据已覆盖）⇒ **留 follow-up**。

## D6. 若验证失败怎么办

本 change **只验证、不修实现**（scope 边界）⇒ 观察报告里如实登记失败项，
**另立 change** 修 `build.md` / `prompts/**`（治理面 ⇒ 需 oracle → critic）。

## 风险与回滚

| 风险 | 缓解 |
|---|---|
| flaky（模型措辞漂） | D1 的「断状态事实」；额度 skip 口径 |
| 污染真实环境的状态文件 | D2 的独立 HOME/DB |
| 「跑得通但没证明什么」 | 每条用例的断言**必须**指向可观测事实（首行形态 / `role.json` 内容），不接受「响应里出现了某个词就算过」 |
| **回滚** | 删除 e2e 仓的新 bats 文件 ⇒ 不影响任何现有产物；层 1 的静态守卫**独立成立**（不依赖层 2） |

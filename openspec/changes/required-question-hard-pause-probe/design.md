# Design — required-question-hard-pause-probe

> 判据真源：`proposal.md` 的「## 验收标准」（AC1–AC5）。本文只记**取舍**。

## D1. 为什么是「探路 change」而不是直接修

`rdd-builder` 的 P0 是**状态机协议**（5 选项 + 落盘）⇒ 加兜底要回答：
- 停机后**状态往哪放**（无落盘 ⇒ 停机 = 丢状态 ⇒ 比「自行选一个」更糟）
- 停机时**列哪些候选**（5 个选项？还是「恢复上一状态」？）
- **恢复路径**（用户下次进来怎么续）

⇒ 这些**全是未知** ⇒ 直接改 = 猜 ⇒ ⇒ **先勘**（v2.42 的 oracle 审原话：「未勘」）。

## D2. 为什么本 change **不加判据**

行为判据要建立在**已知的应该行为**上。勘察之前，「应该行为」是什么都还没定
⇒ 加判据只会把**猜测**固化成契约 ⇒ ⇒ **本 change 零行为判据**，只更新「未覆盖清单」的措辞（AC3）。

## D3. 勘察的最小成本路线

| 步骤 | 成本 | 说明 |
|---|---|---|
| 读 `rdd-builder` skill 的 P0/P2.5 文档 + 状态机代码 | 零 | ⇒ 先答 Q2 / Q4（**可能不必真跑**） |
| 若 Q2/Q4 已回答「有落盘 + 有非交互口径」⇒ | 零 | ⇒ 直接写「无需改动」 |
| 只有前两步答不出 Q1/Q3 ⇒ 才真跑一次 | **1 次 run** | ⇒ 成本受控 |

⚠ **顺序很重要**：先读（零成本）⇒ 再跑（吃额度）⇒ 不要一上来就真跑。

## 风险与回滚

| 风险 | 缓解 |
|---|---|
| 勘察结论依赖 `rdd-builder` 的当前实现 ⇒ 它变了结论就过时 | 报告**标注 `rdd-builder` 的版本/commit** ⇒ 后续 change 实施时复核 |
| 「探路 change」被当成「已修」 | 标题 + AC4 明确「**不改行为**」；守卫清单写「待实施」 |
| **回滚** | 本 change 不改行为 ⇒ 回滚 = 删文档 + 恢复守卫清单措辞 |
